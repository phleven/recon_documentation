Three Write Targets Per Domain

Silver — Iceberg (silver_writer.py)

Raw JSON blob — denormalized. Always written first, best-effort. Never rolled back on downstream failure. Used for AI, analytics, and audit trail. Schema: recon.silver.{domain}

Gold — Iceberg (domain_writer.py)

Normalized tables aligned to HBE schema. Written atomically with HBE. If Gold fails, HBE write does not happen. Schema: biq_gold.{table}

HBE — Postgres (domain_writer.py)

System of record. Written atomically with Gold. One psycopg2 cursor — one transaction. Tables: hbe.person, hbe.person_name, hbe.person_mbrsh, hbe.adr, hbe.person_adr, hbe.person_email, hbe.person_phone, hbe.person_addl_attr, hbe.person_employment, hbe.person_reln

Streaming Model — How Events Flow

Batch-within-a-loop. Each domain service polls Kafka for up to BATCH_SIZE messages per loop iteration, processes each record individually, then commits offsets. BATCH_SIZE is configurable per client.

The Processing Loop

# Each domain service runs this loop continuously
while not stop:
    msgs = consumer.consume(num_messages=BATCH_SIZE, timeout=1.0)
    if not msgs: continue

    for msg in msgs:                      # process each record individually
        event = json.loads(msg.value())
        outcome = process_event(event, ...)  # L1 → L4 → Silver → Gold+HBE

    consumer.commit()                    # commit after full batch processed

One Record Per Domain — What That Means

Person event — one employee

One Kafka message contains all attributes for one employee: name, DOB, gender, addresses[], emails[], phones[]. All sub-records are written in one domain_writer.py call — one HBE transaction.

Employment event — one employment record

One Kafka message = one employment record for one employee. departmentCode, businessUnitCode, payPlan, grade, PSHB eligibility — all in one event.

Relationship event — one dependent

One Kafka message = one dependent. Employee with spouse + 2 children = 3 relationship events on relationship.create. Each processed independently. No employerCode — orgId resolved from PersonCreated.

Throughput Tuning — BATCH_SIZE

BATCH_SIZE valueUse caseBehaviour
1Debugging / dev testingOne record per poll — slowest, easiest to trace
100Default100 records per poll — balanced throughput and latency
500High volume — production catch-up500 records per poll — higher throughput, more memory per loop
1000Bulk load — initial data loadMaximum throughput — use with caution on memory-constrained pods
Set via env var: BATCH_SIZE=100 — see Env Vars tab. Applied per domain service independently — person can run at 100 while employment runs at 500.

Offset Commit Strategy

Current: commit after full batch. If the service crashes mid-batch, the entire batch replays from the first offset on restart. All writes are idempotent — cycle_id + employeeId prevent duplicate HBE rows on replay.

PersonCreated Dependency — Backoff and DLQ

# Employment and Relationship poll person.created before processing
# Retry schedule: 2s → 4s → 8s → DLQ after 3 retries

MAX_RETRIES = int(os.getenv("MAX_RETRIES", "3"))

if not _poll_person_created(employee_id, org_id):
    attempt = event.get("_retry_count", 0) + 1
    backoff = 2 ** attempt                      # 2s, 4s, 8s
    topic = TOPIC_DLQ if attempt >= MAX_RETRIES else TOPIC_IN
    time.sleep(backoff)
    _publish(producer, topic, event)            # requeue or DLQ
    return "REQUEUE"

Two validation layers run sequentially on every event before any write. L1 is structural — field presence and type. L4 is business rules — domain logic, cross-record consistency, duplicate detection.

with get_conn() as conn:
    with conn.cursor() as cur:

# 3. PersonCreated — only published after both Silver and Gold+HBE succeed
